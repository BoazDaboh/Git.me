# Git/Me

Personal Windows developer workstation. Workspace records save through Go to SQLite. Discovery reads project metadata; reviewed local commands use owned Windows process trees. Stages 7a/7b add account connections; Stages 8e/8f add explicitly reviewed Vercel commit deployment and local source upload. Docker remains deferred.

- Keep the Commi admin layout with black/white neutral surfaces, #3981F4 accents, compact controls and light/dark themes.
- Keep copy concise. Avoid decorative text, em dashes and unnecessary comments.
- Never label sample service or deployment status as a verified live reading.
- Do not run project commands, connect accounts, send messages or deploy from interface placeholders.
- Read relevant Next.js guides in node_modules/next/dist/docs before changing framework behavior.
- Keep this project separate from Commi. Do not copy environment files or private data.
- Keep discovery read-only and bounded to the saved project folder. Do not read secret files, run package/Git scripts, follow external linked directories or overwrite profiles without review.
- Process launches must use a saved service and a fresh, single-use review token bound to its folder and command. Never accept arbitrary PIDs for stop, adopt terminal processes, auto-run scanned scripts, or manage Git/Me's own startup services. Keep logs local and bounded; tests must use temporary services and databases.
- GitHub tokens belong only in Windows credential storage. Never return/log/export them or put them in workspace/browser storage. GitHub API traffic must stay on the fixed HTTPS GitHub API host, use read requests only, and not follow authenticated redirects. Tests must use mock responses and isolated credential targets, never the user's actual connection.
- Keep GitHub accounts and activity caches separate. New repository links bind to the chosen permanent account ID. Missing or disconnected accounts must never fall back to another account; older links without an account ID stay bound to the original connection.
- GitHub repository links belong to services, not the project overview. Migrate legacy project links only to unlinked services with matching repository addresses, preserving existing service bindings. Retain unmatched links with their original account in unassignedGitHubLinks for explicit reuse in service pickers. Normalize old browser caches, SQLite reads and imports without discarding notes or bypassing workspace revision checks; persist projected migrations through normal autosave.
- Vercel tokens also belong only in Windows credentials, isolated by account. Keep API traffic on the fixed HTTPS api.vercel.com host, GET only except separately reviewed Stage 8e/8f POST /v13/deployments and Stage 8f POST /v2/files, without authenticated redirects. Whitelist returned fields; never expose environment values, raw provider payloads or arbitrary deployment metadata. Bind links and caches to explicit account/team/project identities and never fall back between accounts. Vercel tests must use simulated responses and isolated credential targets/workspaces.
- Deployment connections belong to saved services. Project Deploy is the service-scoped Setup/Release/Activity workspace, never an independent target. Keep provider/configuration and release actions there; GitHub account/repository controls in Setup and Frontend/Backend share the same service.github link. Local profile, local runtime and health stay in Frontend/Backend. Preserve one authoritative service link and all existing review protections. Host command and environment-name records are reference only and must never imply a provider settings write. Reuse a legacy project link only after a fresh original-account/team/project check verifies the exact service GitHub repository. Preserve existing service links and all unrelated workspace fields; move the legacy link through revision-checked autosave. Release history always keeps its original immutable target.
- Stage 8a is setup/review only: release inspection accepts saved service IDs, reads bounded Git metadata and checks tool presence without executing tools or project code. Do not follow Git metadata outside saved project boundaries. Never imply that read access, a detected executable or a selected environment proves push/deploy permission or automatic deployment behavior.
- Stage 8b Local Git only accepts saved service IDs and fixed operations. Stage/unstage/commit require an expiring single-use review bound to the actual repository/index/HEAD/selected content. Never accept shell commands, arbitrary folders or unreviewed writes. Keep private files and filters blocked; suppress hooks, fsmonitor, external diff/text conversion, signing and lazy fetching. Use temporary indexes and compare-and-swap updates without altering working files or other services' staging. Tests may write only temporary repositories.
- Stage 8c pushes only an explicitly reviewed commit to the same named branch on a saved, matching HTTPS github.com origin. Bind expiring single-use reviews to saved service/link identity, repository, configuration, branch, HEAD and observed remote tip. Reject diverged history; no force pushes, merges, tags or automatic retries. Use isolated Git configuration and an owned Windows process tree with only the bundled Git Credential Manager; never reuse dashboard tokens or permit repository credential/SSH/proxy helpers, hooks, redirects or arbitrary network destinations. Clearly distinguish accepted pushes from follow-up verification and possible provider-triggered deployments. Tests may push only to temporary fixture repositories. Direct deployment is a separate reviewed Stage 8e action.
- Stage 8d stores accepted pushes or explicitly verified existing GitHub commits in a separate SQLite release history. Keep account/team/project bindings fixed per record; changing a service link must never retarget older releases. Match Vercel deployments by exact SHA, branch and saved project scope, checking GitHub repository metadata when available. Missing deployments stay unobserved; READY does not establish current production unless the provider's production target matches the deployment ID. Preserve push success independently of deployment errors. Provider tracking is GET only, bounded and cached; exclude raw metadata, environment values and credentials. Test only with isolated databases and simulated cloud responses.

- Stage 8e requests only a recorded GitHub SHA and branch from the saved service's matching Vercel project. Review is read-only and expires after five minutes; execution consumes a single-use review and rechecks saved source, account token, owner/team/project and Git integration. The only provider write is one POST /v13/deployments with exact gitSource and reviewed Preview/Production target; no local files, environment values, project-setting overrides, redirects or automatic retries. Record submission in a separate SQLite deployment_actions journal before sending and preserve accepted, rejected and unconfirmed outcomes through refresh/restart. Request acceptance is not build success or current production. Tests use only temporary workspaces and simulated provider writes.

- Stage 8f uses only saved service/project IDs, its bounded local folder and explicit service Vercel link. Never accept browser-supplied paths, file bytes, provider settings or credentials. Review lists metadata only and uploads nothing. A five-minute single-use confirmation rechecks a SHA-256 source snapshot and account/team/project binding before uploading immutable bytes. Exclude private/generated paths, common credential content and linked files, combine local/nested ignore exclusions conservatively, reject unsupported ignore syntax and nested provider Root Directories. Share the per-service submission guard with 8e. Journal before the first file POST, send each file and deployment request once without automatic retries or redirects, and preserve partial/uncertain outcomes. Track local builds by exact returned deployment ID and verified project, never by a fabricated Git SHA. No Git operations, provider settings writes or local project command execution. Tests use temporary source/SQLite and simulated API writes only.

- API testing uses a saved project/service scope. GET starts only on Send or Run saved GET checks; JSON POST requires a five-minute single-use server review bound to the captured URL, headers, body and saved scope, followed by explicit confirmation. Review/cancel must never contact the target. Do not accept arbitrary methods or payload overrides during execution, or retry a POST automatically; interrupted writes must report uncertain delivery. Never run servers, follow redirects, disable TLS verification, reuse dashboard/cloud credentials, use environment proxies or log request URLs/headers/bodies. Permit explicit HTTP(S) localhost/LAN/public targets while blocking the app/companion ports, metadata/link-local/unspecified/multicast destinations; validate DNS addresses and dial those addresses directly. Bound headers, decoded body, time and concurrency; propagate cancellation. Render responses as escaped text. Persist only validated per-project request names, GET/POST methods, URL paths, service IDs, timestamps and optional expected status codes (200-599), excluding queries, headers, JSON bodies, review tokens and responses from SQLite/cache/export. Saved checks accept only saved project/request IDs, re-read the definition, reject POST and orphaned service references, use no editor headers or query values, and read status only. Run sequentially on explicit click, cancel the queue on stop/unmount, keep outcomes in session memory, and mark results stale when the saved definition changes. Older records default to expected 200. Review payloads stay only in bounded, expiring memory; cancellation, replay and saved scope changes must invalidate them. Tests use temporary HTTP fixtures and workspaces, never user services.
