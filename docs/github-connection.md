# Stage 7a: connect GitHub

Docker is deferred. This stage adds a read-only GitHub connection; Vercel is a later addition.

## Connect your account

1. Open Git/Me > Settings > GitHub accounts. Use Add account for another account.
2. Click Create GitHub token. This opens GitHub's own site; sign in there if needed.
3. Create a fine-grained personal access token named GitMe.
4. Choose its resource owner and Only select repositories. Start with Commi or another repository you want to inspect.
5. Under Repository permissions, choose Contents: Read-only and Pull requests: Read-only. Metadata read access is included. Check these settings even if the link prefilled them.
6. Set an expiry and generate the token.
7. Copy the full generated token, including its `github_pat_` prefix, into Git/Me's Personal access token field, then click Test & connect. Do not enter the token's name.

Git/Me verifies the token with GitHub's account endpoint, shows your account name, and saves it using Windows Credential Manager. The private input clears after a successful connection. A failed attempt keeps the masked input for correction and shows an error. Do not paste the token into chat, notes, service commands or environment fields.

The connection uses your token rather than your GitHub password. Git Bash's existing login is separate and is not automatically reused. The current implementation connects to GitHub.com, not a custom Enterprise Server hostname.

## Multiple accounts

Connections recheck automatically when internet access returns, when you return to the app, and when the local companion recovers. Reconnect checks request fresh readings and coalesce repeated events. A follow-up check after about eleven seconds clears a recently cached failure. Minute polling continues while the tab is visible; expired/revoked tokens still need replacement.

Use Add account with a token generated by the other GitHub account. Existing connections stay connected. Each account has its own Replace token and Disconnect controls. Adding another token for the same account updates that account instead of creating a duplicate. Replace token only accepts a token belonging to that same account.

The original single-account connection is picked up automatically. Existing repository links continue using it. New links store the chosen GitHub account's permanent numeric ID. The companion verifies accounts independently, with separate activity caches. It supports up to ten saved connection records on this PC.

## Link a repository

1. Open Projects and choose a project.
2. Open Deploy > Setup, choose a service, and click Link repository in its GitHub panel. The same controls are also available in Frontend, Backend or Other services.
3. Choose the GitHub account, then select a repository from its list, or enter `owner/repository` and click Look up repository.
4. Click Link selected repository and wait for Saved to SQLite.

The list is paginated. Filtering applies to the current page; owner/repository lookup checks a specific repository directly. Only repositories accessible with the token can be read. A public repository appearing in the list does not prove access to private repositories.

Repository URLs already saved in service profiles can appear as suggestions. Suggestions do not link anything automatically.

GitHub repository configuration lives under services. The project overview no longer has a separate GitHub tab. Each service's chosen repository is shared by its activity, release checks and deployment workflow. Frontend and backend can use different repositories, or share one repository for a monorepo. Linking updates the service's saved repository URL. Unlinking removes its GitHub activity link without deleting the repository or its source URL. Hosting-provider links remain separate service settings.

Services can choose different accounts. Disconnecting one account keeps its repository links, clears its displayed activity, and leaves other connections working. Git/Me never silently switches those links to a different account. Use Change repository to choose another account explicitly.

## Existing project links

Older project-level links move automatically to services whose repository address matches. Existing service links and their chosen accounts take priority and are never overwritten. An unmatched link is retained in the project's saved metadata and appears as **Saved: owner/repository** inside service repository pickers. Selecting it uses its original account, verifies the repository again, then saves it on that service. A disconnected original account must be reconnected; it does not fall back to another account.

SQLite reads expose the normalized service links immediately. Browser caches and old workspace imports are normalized too. Changes persist through normal revision-checked autosave, including any pending note edits. Account tokens remain untouched in Windows credentials. Project-only GitHub activity requests are no longer supported; activity requests require a service ID.

## What Git/Me displays

- The linked repository's visibility, default branch and archived state.
- Up to five recent commits on the default branch.
- Up to five recently updated open pull requests.
- Up to ten branches, with a link to GitHub's full branch view.
- The last check time and any permission or connectivity errors.

Activity refreshes about once a minute while visible. The companion caches results for up to a minute; manual refresh has a ten-second minimum interval. Multiple profiles linked to the same repository can reuse that cache.

If commits are available but pull-request access is denied, the available sections remain visible and the denied section is labelled unavailable. An empty repository may have no commit or branch activity yet.

Remote requests use GitHub's read endpoints only. There are no commit, push, merge, repository creation or deployment actions in this integration. Clicking a commit or pull request opens its page on GitHub.

## Where information is stored

| Information | Location |
| --- | --- |
| Original connection token | Windows credential storage, target `GitMe/GitHub/api.github.com` |
| Additional account tokens | Separate Windows credential targets under `GitMe/GitHub/accounts/` |
| Local account index (IDs and usernames, no tokens) | Windows credential target `GitMe/GitHub/connections` |
| Repository ID, owner/name and chosen account ID | SQLite workspace records and workspace exports |
| Account verification and repository activity cache | Go companion memory |
| Token input | Temporary form state, cleared after success or leaving the settings page |

The token is not saved in SQLite, browser localStorage, source files or exports, and is not returned by the companion. It is sent from the private input to your local companion and then to GitHub over HTTPS. If Windows credential storage fails, Git/Me does not fall back to a plaintext file.

Export/import transfers repository links and their account IDs, not account credentials. Connect the same accounts again on another PC. Older links without an account ID use the original local connection; explicitly relink them when moving PCs. Replacing a token tests the new one before replacing the old credential; an invalid replacement keeps the previous connection.

Disconnect removes only that account's saved credential from this PC and clears its companion cache. Repository links remain. It does not revoke the token at GitHub; revoke it from GitHub's token settings if you want to invalidate it there too. Unlink changes only the selected project or service link. The original connection's non-secret identity is retained locally to prevent older links from adopting another account.

## Common issues

- Invalid/expired token: create a replacement and use Replace token, or remove the local connection with Disconnect.
- Repository not found: check spelling, resource owner, selected repositories and token expiry. A private repository without permission may also return not found.
- Organisation access denied: the organisation may require token approval or have its own token policy. Resolve this in GitHub.
- Pull requests unavailable: check Pull requests: Read-only on the token.
- Rate limit reached: wait before refreshing. The integration does not keep retrying aggressively.
- Integration unavailable: restart the updated Go companion, then refresh Git/Me.
- Old data with an error: the timestamp marks the last successful reading. It is not a new verified status.
- Repository renamed/transferred: look up its current owner/name and relink. Git/Me checks repository identity and does not follow authenticated redirects automatically.
